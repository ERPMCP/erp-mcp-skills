ERP MCP 与系统导出表字段对照及 Skill 编写规则（优化版）
版本日期：2026-07-14
适用范围：所有使用同类 ERP 的公司；文档不包含任何特定公司、门店或人员名称。

================================================================
零、文件使用建议：Excel 是否适合直接放入 Skill
================================================================

结论：Excel 可以放入 Skill，但不建议作为唯一知识文件。
推荐同时保留以下文件：
1. SKILL.md：放工具选择、强制规则、决策流程和导出触发条件。
2. 本 TXT：放完整说明、字段解释、统计口径、场景方案和导出模板。
3. TSV 字段矩阵：放 165 个字段的机器可读对照，Codex 可直接按行读取或 grep。
4. XLSX：用于人工筛选、维护、审计和更新字段，不作为运行时唯一依赖。

原因：
- TXT/Markdown 可以直接搜索和读取，不需要解析库。
- TSV 是严格的行列结构，适合代码和模型快速定位字段。
- XLSX 的视觉维护体验最好，但读取成本更高，且 Skill 运行环境不一定总能直接解析。

建议 Skill 目录：
skill-name/
  SKILL.md
  references/
    ERP_MCP与导出表字段对照_优化版.txt
    ERP_MCP与导出表字段能力矩阵_优化版.tsv
    ERP_MCP与导出表字段能力矩阵_优化版.xlsx

================================================================
一、优化版核心结论
================================================================

系统导出能力共整理 7 个表格模块、165 个字段项：
- MCP直接支持：88 项。
- MCP部分支持、层级或枚举需核对：10 项。
- MCP可通过组合计算得到：1 项。
- MCP不支持、需要客户导出：66 项。

最大能力缺口：
1. 完整组织结构：运营、大区、片区、门店、分组及其层级关系。
2. 完整人员名册：工号、职能、岗位、入职、离职、冻结、最近登录等。
3. 合同双方经纪人的完整组织归属。
4. 交易性质、有无抵押、房源侧带看次数。
5. 业绩小组、总实收业绩等导出表特有字段。
6. queryRptData 统计日期底层口径不透明，不能直接认定为签约日期或结单日期。

二、与旧版/Codex文档相比的关键修正
================================================================

1. 问题：合同关联键写成仅使用“合同编号”。
   修正：统一使用“合同类型 + 去除首尾空格后的合同编号”；合同编号按文本处理并保留前导零。
   依据：实际样例存在合同编号首尾空格；不同业务类型可能出现相同编号。
   Skill影响：避免跨业务类型错配合同，以及编号被转数字后丢失前导零。
   优先级：最高

2. 问题：把人员信息的第一个工作表称为“架构 Sheet”。
   修正：实际工作表名称为“汇总”；Skill 应优先按表头特征识别，不应写死名称。
   依据：源表工作表名为“汇总”。
   Skill影响：避免找不到工作表。
   优先级：最高

3. 问题：把人员“汇总”表字段写成运营、大区、片区、门店、分组。
   修正：准确字段为：运营、大区、片区、门店、人数；该表没有分组字段。
   依据：源表表头共5列。
   Skill影响：避免把人数当成组织字段，也避免人均分母计算错误。
   优先级：最高

4. 问题：人员列表字段中出现“在职、转正时间、业务范围、户籍、学历、常用电话、个人简介”等非当前样例表头。
   修正：改为源表46个准确字段，并补回离职时间、冻结、冻结时间、提成方案、公积金号、备用电话、荣誉奖项等。
   依据：源表人员列表表头核验。
   Skill影响：保证Skill只引用真实可导出的字段。
   优先级：最高

5. 问题：合同字段被改写为“抵押状况、租赁抵押、押金数”。
   修正：保留实际字段名：交易性质、有无抵押、押金金额；不存在“租赁抵押”列。
   依据：合同信息导出表实际56个表头。
   Skill影响：避免导出指导出现不存在的列名。
   优先级：最高

6. 问题：付款明细字段有时写成“项目”。
   修正：准确原始字段名为“科目”；标准字段可映射为款项类型。
   依据：付款明细导出表表头。
   Skill影响：避免客户在导出文件中找不到字段。
   优先级：高

7. 问题：人员“汇总”表被描述为完整组织树。
   修正：该表只有运营、大区、片区、门店、人数，且“门店”值可能带组名；完整人员归属应结合“人员列表”。
   依据：源表结构及样例值。
   Skill影响：避免把汇总快照误当成完整层级字典。
   优先级：高

8. 问题：MCP房源筛选中的数组参数被描述为逗号分隔字符串。
   修正：houseTypes、towards、decoration、floorRanges 按 schema 传字符串数组；rooms 才是字符串。
   依据：MCP schema。
   Skill影响：避免工具调用参数类型错误。
   优先级：高

9. 问题：periodRanges 被解释为挂牌时间范围，periodUniq 被解释为一般唯一性。
   修正：periodRanges 是房屋年限特色（如满两年）；periodUniq 是满五唯一。
   依据：MCP schema。
   Skill影响：避免房源筛选语义错误。
   优先级：高

10. 问题：未充分说明一对多表直接连接会重复金额。
   修正：新增表粒度和防重复规则：应收应付、业绩分配、实收、付款均为一对多，合并前按目标粒度聚合。
   依据：实际导出样例中同一合同存在多条科目、分配角色和收付款记录。
   Skill影响：避免合同数、应收、总实收佣金等被倍增。
   优先级：最高

================================================================
三、Skill 必须遵守的总流程
================================================================

步骤1：识别用户要的是统计值、具体明细、房源、小区行情、组织分析还是人员分析。
步骤2：优先调用 MCP；不要一开始就要求客户导出全部表格。
步骤3：确认日期口径：签约、结单、录入、支付、付款创建或人员快照。
步骤4：检查 MCP 返回字段是否足够，以及 deptName/assignDeptName 是否能证明具体组织层级。
步骤5：字段不足时，只要求客户导出指定表、指定时间段和最小必要字段。
步骤6：按复合键清洗、去重或聚合后再合并；禁止直接把多个一对多表连接后求和。
步骤7：输出必须说明数据来源、日期口径、人员口径、是否存在统计与明细差异。
步骤8：默认脱敏，不要求客户导出与需求无关的身份证、银行卡、地址等字段。

4.2 queryContractFinanceData：合同、财务、业绩明细

支持 type：合同明细、实收明细、应收应付、业绩分配、付款明细。
单次日期范围不超过31天。paymentDateBegin/paymentDateEnd 与 settlementDateBegin/settlementDateEnd 二选一；参数名与实际业务口径可能不完全一致，应按 type 的工具说明和返回日期字段核对。

日期口径：
- 合同明细：工具说明为按签约日期。
- 实收明细：按支付日期。
- 应收应付：按签约日期。
- 业绩分配：按签约日期。
- 付款明细：按付款创建日期。

4.3 房源工具
- listHouseByCondition：按出售/出租、区域、商圈、小区、价格、面积、户型、朝向、装修、楼层、电梯、房龄、满两年、满五唯一、钥匙、新上等筛选。
- getHouseByHouseNo：按房源编号查询单套房源详情。
参数纠正：houseTypes、towards、decoration、floorRanges 为字符串数组；rooms 为字符串；periodRanges 表示满两年等年限特色；periodUniq 表示满五唯一。

4.4 小区行情工具
- getSectionMarketBaseInfo：小区名称、区域、板块、经纬度等基础信息。
- getSectionMarketData：看板、价格趋势、流动性、成交均价、户型分布、挂牌均价、成交周期、看房量、竞争力。
- listHotSection：成交、带看、浏览、挂牌、分享等热门小区榜单。

4.5 MCP 当前不能完整提供
- 完整组织树、全部门列表、全员工列表、在职人数、岗位职能、人事状态。
- queryRptData 指标底层 SQL 和日期字段定义。
- 官方的统计值直接钻取合同号接口。
- 写入、修改、删除、审批、结佣等操作。

================================================================
五、系统导出表自动识别规则
================================================================

【付款明细导出】
- 可能工作表名：1、付款明细或其他默认名
- 必备表头特征：合同类型、合同编号、类型、科目、金额、付款日期
- 字段数：11
- 数据粒度：一行一笔付款/退款科目记录
- 推荐日期字段：付款创建日期或付款日期
- 主要关联键：合同类型+合同编号；行级再加付款日期+金额+类型+科目
- 注意：不要依赖文件名中的月份；退款符号和状态需核对。

【合同信息导出】
- 可能工作表名：1、合同信息或其他默认名
- 必备表头特征：结单状态、产权地址、卖方/房东经纪人、买方/租客经纪人、签约日期
- 字段数：56
- 数据粒度：通常一行一份合同
- 推荐日期字段：签约日期；结单分析另用结单日期
- 主要关联键：合同类型+合同编号
- 注意：同一编号跨合同类型可能重复；编号常带首尾空格。

【实收明细导出】
- 可能工作表名：1、实收明细或其他默认名
- 必备表头特征：佣金来源、支付金额、支付日期、票据号码
- 字段数：13
- 数据粒度：一行一笔实收记录
- 推荐日期字段：支付日期
- 主要关联键：合同类型+合同编号；行级优先票据号码
- 注意：相同合同、日期和金额可能是合法多笔，也可能重复，不能只按金额去重。

【业绩明细导出-应收应付】
- 可能工作表名：应收应付
- 必备表头特征：应收金额、应收科目、应付科目、应付金额、签约日期
- 字段数：14
- 数据粒度：一行一个合同-应付科目组合
- 推荐日期字段：签约日期；结单分析另用结单时间
- 主要关联键：合同类型+合同编号+应收科目+应付科目
- 注意：应收金额可能在多条应付科目行重复，直接求和会虚高。

【业绩明细导出-业绩分配】
- 可能工作表名：业绩分配
- 必备表头特征：经纪人、业绩门店、分配类型、分配比例、分配业绩、总实收业绩
- 字段数：20
- 数据粒度：一行一个合同-人员-分配角色
- 推荐日期字段：签约日期；结单分析另用结单时间
- 主要关联键：合同类型+合同编号+经纪人+分配类型+应收科目
- 注意：总实收佣金常在同一合同多条分配行重复，不能逐行求和。

【人员信息导出-汇总】
- 可能工作表名：汇总
- 必备表头特征：运营、大区、片区、门店、人数
- 字段数：5
- 数据粒度：一行一个汇总组织节点
- 推荐日期字段：导出时点快照
- 主要关联键：运营+大区+片区+门店
- 注意：没有分组列；“门店”值可能包含组级名称，只能视为原始部门标签。

【人员信息导出-人员列表】
- 可能工作表名：人员列表
- 必备表头特征：姓名、工号、离职、冻结、最近登录时间、入职日期
- 字段数：46
- 数据粒度：一行一个人员账号/档案
- 推荐日期字段：导出时点快照
- 主要关联键：工号优先；否则姓名+门店/分组
- 注意：历史组织归属无法仅凭当前快照还原。

六、每个导出模块的准确字段及 MCP 补充关系
================================================================

6.1 付款明细导出 / 付款明细
字段数：11
支持统计：直接支持 11项
准确原始字段：
合同类型、合同编号、签约时间、类型、科目、状态、金额、付款方式、付款人、备注、付款日期。

字段逐项说明：
- 合同类型：标准名=合同类型；含义=合同所属业务类型；状态=MCP直接支持；MCP映射=queryContractFinanceData / 付款明细 → contractType；处理=优先直接用MCP查询。；说明=与合同编号组成合同唯一键。；敏感级别=普通；需导出=否。
- 合同编号：标准名=合同编号；含义=合同编号；状态=MCP直接支持；MCP映射=queryContractFinanceData / 付款明细 → contractNo；处理=优先直接用MCP查询。；说明=必须按文本处理并清理首尾空格。；敏感级别=中敏；需导出=否。
- 签约时间：标准名=签约日期；含义=合同签约日期；状态=MCP直接支持；MCP映射=queryContractFinanceData / 付款明细 → contractDate；处理=优先直接用MCP查询。；说明=不要与付款日期混用。；敏感级别=普通；需导出=否。
- 类型：标准名=付款类型；含义=实付或退款；状态=MCP直接支持；MCP映射=queryContractFinanceData / 付款明细 → 付款类型；处理=优先直接用MCP查询。；说明=枚举通常为实付/退款。；敏感级别=普通；需导出=否。
- 科目：标准名=款项类型；含义=付款对应款项科目；状态=MCP直接支持；MCP映射=queryContractFinanceData / 付款明细 → 款项类型；处理=优先直接用MCP查询。；说明=—；敏感级别=普通；需导出=否。

================================================================
八、数据关联、字段清洗与日期口径
================================================================

【合同唯一键】
统一使用“合同类型 + 清理首尾空格后的合同编号”。合同编号始终按文本处理，保留前导零，不要直接转数字。
原因/风险：不同合同类型可能出现相同合同编号；原始编号可能带空格或前导零。

【业绩分配行唯一键】
建议使用“合同类型 + 合同编号 + 经纪人 + 分配类型 + 应收科目”，必要时再加分配金额。
原因/风险：同一合同会拆成多个人、多种角色、多种科目。

【实收/付款去重键】
建议使用“合同类型 + 合同编号 + 日期 + 金额 + 科目/类型 + 人员”，如有票据号则优先加入票据号。
原因/风险：同一合同可能在同一天有多笔同金额记录，单纯按合同号会误去重。

【人员唯一键】
优先使用工号。没有工号时使用“姓名 + 门店/分组”，并保留人工复核清单。
原因/风险：姓名可能重复，且人员可能调店。

【组织口径】
明确分析使用“当前组织”还是“业务发生时组织”。当前人员表通常只能代表导出时点。
原因/风险：人员调店后，用当前组织回填历史业务会产生错归属。

【人数口径】
必须事先定义：期末在职人数、期初在职人数、期间平均在职人数、参与业务人数或账号人数。
原因/风险：不同分母会导致人均指标和开单率差异很大。

【日期口径】
每次让客户导出时，必须记录导出页面选择的日期字段、开始日期、结束日期和导出时间。
原因/风险：文件名中的月份不能证明筛选口径；MCP不同类型的日期口径也不相同。

【MCP 31天限制】
日期跨度超过31天时，按自然月或不超过31天窗口拆分调用，再合并。
原因/风险：queryRptData和合同财务明细工具都有日期范围限制。

【统计与明细关系】
queryRptData用于统计值；合同明细/业绩分配用于明细核对。三者不一致时必须展示差异，不强行对齐。
原因/风险：统计归属口径可能与合同明细条数不同。

【金额标准化】
成交金额/租金可能混合“万元”和“元/月”；金额字段可能是文本。计算前必须拆分业务类型和单位。
原因/风险：直接求和会产生数量级错误。

【退款处理】
付款/实收分析必须明确退款是正数配合类型字段，还是负数金额；审核未通过记录是否纳入也要定义。
原因/风险：不同系统导出和MCP返回可能采用不同符号。

【部门字段风险】
MCP中的deptName/assignDeptName是通用部门名，不能默认等于门店或小组。
原因/风险：组织层级未公开，且不同公司组织结构不同。

【最小化导出】
只指导客户保留解决问题所需字段，默认删除身份证、银行卡、社保、公积金、详细地址、紧急联系人等无关敏感字段。
原因/风险：降低隐私泄露和误用风险。

【脱敏规则】
证件号和手机号默认仅保留前3后4；详细地址默认保留到小区级；姓名对外展示可使用姓氏+先生/女士或编号。
原因/风险：合同和人员导出包含大量个人敏感信息。

【通用化要求】
Skill和分析模板中不得写死公司名、门店名、人员名或具体组织层级名称；组织层级按导出字段动态识别。
原因/风险：确保所有公司可复用。

【缺失字段处理】
MCP未支持字段优先要求客户导出指定表和时间段；不要通过备注文本猜测结构化字段。
原因/风险：备注自由文本不稳定，容易误判。

新增清洗规则：
1. 表头统一去首尾空格、全角空格和换行；保留原始字段名映射。
2. 合同编号、房源编号、工号、票据号码全部按文本读取，禁止自动转数值。
3. 合同编号去除首尾空格，但不要删除中间连字符、字母或前导零。
4. 日期无法解析时保留原始值并进入异常清单，不得静默转换。
5. 成交金额/租金同时包含万元和元/月，必须按合同类型与单位分别计算。
6. deptName/assignDeptName 只能称为部门字段，除非组织字典能证明其是门店或分组。
7. 人员源表使用“离职”“冻结”，在职状态必须根据明确业务规则推导。

================================================================
九、一对多关系和防重复汇总规则
================================================================

【合同信息】
- 原始粒度：通常一合同一行
- 常见重复来源：少数系统可能因附件/子协议拆行
- 禁止：直接按行数当合同数
- 正确处理：按合同类型+合同编号去重后统计合同数
- 可安全汇总：成交金额/租金、双方佣金（确认一合同一行后）
- 需去重/单独处理：备注、地址等文本

【应收应付】
- 原始粒度：合同×应收科目×应付科目
- 常见重复来源：一个合同有多个应付科目，应收金额重复展示
- 禁止：逐行合计应收金额
- 正确处理：应收先按合同键+应收科目取唯一值；应付按行汇总
- 可安全汇总：应付金额
- 需去重/单独处理：应收金额、合同数

【业绩分配】
- 原始粒度：合同×人员×分配类型×科目
- 常见重复来源：同一合同拆多人员、多角色；总实收佣金重复
- 禁止：把总实收佣金逐行求和
- 正确处理：分配业绩按唯一分配行汇总；总实收佣金按合同键+科目去重
- 可安全汇总：分配业绩、总实收业绩（先保证行唯一）
- 需去重/单独处理：总实收佣金、合同数

【实收明细】
- 原始粒度：一笔实收流水
- 常见重复来源：同合同可同日多笔同金额；票据号可能合并多个号码
- 禁止：仅按合同号或合同号+金额去重
- 正确处理：优先使用票据号；无票据号时保留原始行并用复合键标记疑似重复
- 可安全汇总：支付金额（明确审核/退款口径后）
- 需去重/单独处理：合同数、重复流水判断

【付款明细】
- 原始粒度：一笔付款/退款科目流水
- 常见重复来源：同合同同日多个科目或多次退款
- 禁止：把退款金额无条件当负数或逐合同只保留一行
- 正确处理：根据类型字段决定正负；行级键加入日期、金额、类型、科目、付款人
- 可安全汇总：金额（统一正负规则后）
- 需去重/单独处理：合同数、付款笔数

【人员列表】
- 原始粒度：一人员账号/档案
- 常见重复来源：同名人员、调店、重复账号
- 禁止：用姓名单字段关联历史业务
- 正确处理：优先工号；无工号使用姓名+组织并输出冲突清单
- 可安全汇总：人数（按明确离职/冻结口径）
- 需去重/单独处理：历史组织归属

【跨表合并】
- 原始粒度：合同主表1对多连接财务/业绩表
- 常见重复来源：先连接多个子表会产生笛卡尔积
- 禁止：合同→实收→业绩分配直接逐行连接后汇总
- 正确处理：每个子表先聚合到目标粒度，再与合同主表连接
- 可安全汇总：聚合后的指标
- 需去重/单独处理：任何原始行级金额

特别强调：
- 应收应付表中的应收金额可能因不同应付科目重复，不能逐行合计。
- 业绩分配表中的总实收佣金可能在同一合同的每个分配行重复，不能逐行合计。
- 多个一对多子表先连接再汇总会形成笛卡尔积，必须先各自聚合。
- 合同份数统一按“合同类型+合同编号”去重。

================================================================
十、客户需求解决方案
================================================================

【需求：某时间段合同成交单量/金额/应收/实收统计】
- MCP先查：queryRptData：合同成交单量·份、合同应收·元、合同实收·元
- 需导出：通常不需要
- 建议字段：—
- 时间范围：—
- 合并键：按部门/人员汇总，无明细合并
- 计算逻辑：统计值优先按MCP口径；跨度超过31天需拆分查询后合并。
- 口径风险：queryRptData日期底层口径未公开；不能直接等同签约日期或结单日期。
- 隐私要求：仅汇总数据，风险较低。

【需求：统计值对应哪些具体合同】
- MCP先查：queryRptData + queryContractFinanceData（合同明细、业绩分配）
- 需导出：口径不一致时再导出“合同信息导出”
- 建议字段：合同类型、合同编号、签约日期、结单日期、结单状态、业绩分配状态、签约门店/小组
- 时间范围：与统计查询相同，并记录导出筛选字段
- 合并键：合同类型 + 合同编号
- 计算逻辑：先核对合同明细条数，再核对业绩分配中的合同数；仍不一致时用导出表定位。
- 口径风险：统计值不一定等于合同明细条数；合同编号必须按文本清洗空格。
- 隐私要求：不需要客户、业主证件号。

【需求：按运营/大区/片区/门店/分组分析成交、业绩或实收】
- MCP先查：合同明细、业绩分配、实收明细
- 需导出：人员信息导出（人员列表）；必要时合同信息导出
- 建议字段：工号、姓名、运营、大区、片区、门店、分组、职能、入职日期、离职状态/时间
- 时间范围：人员表建议导出分析截止日的最新快照
- 合并键：优先工号；无工号时使用姓名 + 门店/分组
- 计算逻辑：将MCP中的人员姓名映射到人员组织层级，再按组织维度汇总。
- 口径风险：同名人员会误匹配；组织调动需明确按当前组织还是历史组织。
- 隐私要求：不要导出身份证、银行卡、地址等无关字段。

【需求：门店人均开单量、开单率、人均业绩】
- MCP先查：queryRptData成交单量/业绩指标，或业绩分配明细
- 需导出：人员信息导出（汇总或人员列表）
- 建议字段：运营、大区、片区、门店、分组、姓名、工号、入职日期、离职状态、离职时间
- 时间范围：与统计期匹配的人员快照；最好保留期初、期末状态
- 合并键：组织字段；个人明细用工号/姓名+组织
- 计算逻辑：分子用MCP统计或业绩；分母按明确口径统计在职人数、平均在职人数或参与业务人数。
- 口径风险：不能用有业务记录人数代替在职人数；开单率需先定义分母。
- 隐私要求：仅保留组织和在职状态字段。

【需求：房源方与客源方分别按组织层级统计】
- MCP先查：合同明细中的houseUserName、custUserName
- 需导出：合同信息导出，或人员信息导出做人员组织映射
- 建议字段：房源方/客源方经纪人、职能、分组、门店、片区、大区、运营
- 时间范围：合同签约日期范围
- 合并键：合同类型 + 合同编号；或经纪人 + 组织
- 计算逻辑：分别构建房源方与客源方维度，再统计合同数、佣金、成交周期等。
- 口径风险：MCP只提供经纪人姓名，不提供双方完整组织层级。
- 隐私要求：无需导出客户/业主证件号。

【需求：分析房源带看次数、房源成交周期与成交结果】
- MCP先查：合同明细中的houseDealPeriod；可辅以queryRptData带看统计
- 需导出：合同信息导出
- 建议字段：合同类型、合同编号、小区名称、房源侧带看次数、房源成交周期、签约日期、成交金额/租金
- 时间范围：合同签约日期范围
- 合并键：合同类型 + 合同编号
- 计算逻辑：按带看次数分段，比较成交周期、成交价及佣金。
- 口径风险：queryRptData带看是汇总口径，不能替代单合同的房源侧带看次数。
- 隐私要求：地址保留到小区级即可。

【需求：分析交易性质、抵押状态与成交/结单】
- MCP先查：合同明细
- 需导出：合同信息导出
- 建议字段：合同类型、合同编号、交易性质、有无抵押、签约日期、结单状态、结单日期、成交金额/租金
- 时间范围：合同签约日期范围
- 合并键：合同类型 + 合同编号
- 计算逻辑：将导出补充属性并入MCP合同明细后分组分析。
- 口径风险：交易性质的枚举含义需由系统业务人员确认。
- 隐私要求：不需要产权地址、证件号、产权证号。

【需求：实收按签约分组、门店或人员分析】
- MCP先查：queryContractFinanceData（实收明细）
- 需导出：需要精确签约分组时导出“实收明细导出”
- 建议字段：合同类型、合同编号、签约门店、签约分组、签约人、科目、支付金额、支付日期
- 时间范围：按支付日期
- 合并键：合同类型 + 合同编号 + 支付日期 + 金额 + 科目（必要时）
- 计算逻辑：MCP提供金额与人员，导出补充签约分组后汇总。
- 口径风险：MCP status值含义未公开；重复款项需用复合键去重。
- 隐私要求：无需票据号码和备注时不要导出。

【需求：业绩按小组、角色、实收进度分析】
- MCP先查：业绩分配 + 实收明细
- 需导出：业绩明细导出（业绩分配）
- 建议字段：合同类型、合同编号、经纪人、业绩门店、业绩小组、分配类型、分配比例、分配业绩、总实收佣金、总实收业绩
- 时间范围：通常按签约日期；另记录实际导出筛选口径
- 合并键：合同类型 + 合同编号 + 经纪人 + 分配类型
- 计算逻辑：MCP提供分配金额；导出补充业绩小组和实收业绩，实收佣金可与MCP实收明细交叉核对。
- 口径风险：总实收业绩不能直接等同分配业绩；退款和未审核款项需单独处理。
- 隐私要求：人员姓名属于中敏，内部使用。

【需求：合同应收、应付及费用科目分析】
- MCP先查：queryContractFinanceData（应收应付）
- 需导出：通常不需要；仅在部门层级不明确时导出
- 建议字段：合同类型、合同编号、签约门店、应收金额/科目、应付金额/科目、签约日期
- 时间范围：按签约日期
- 合并键：合同类型 + 合同编号 + 应收科目 + 应付科目
- 计算逻辑：直接按MCP明细汇总，避免把多条应付科目当作多份合同。
- 口径风险：一份合同可能有多条应付科目，合同数必须去重。
- 隐私要求：地址字段可不取。

【需求：付款、退款、付款方式及付款人分析】
- MCP先查：queryContractFinanceData（付款明细）
- 需导出：通常不需要
- 建议字段：—
- 时间范围：按付款创建日期/付款日期，需确认系统筛选口径
- 合并键：合同类型 + 合同编号 + 付款日期 + 金额 + 付款类型
- 计算逻辑：按付款类型区分实付与退款，再按科目、方式、付款人统计。
- 口径风险：退款正负号和审核状态枚举需核对实际返回。
- 隐私要求：付款人姓名和备注按需展示。

【需求：离职员工历史业绩、离职前后产能】
- MCP先查：业绩分配、合同明细、queryRptData
- 需导出：人员信息导出（人员列表）
- 建议字段：工号、姓名、组织层级、入职日期、离职状态、离职时间
- 时间范围：最新人员快照；若有组织历史需另取历史快照
- 合并键：工号优先；否则姓名 + 组织
- 计算逻辑：按签约/业绩日期与入离职日期判断当时是否在职，再比较阶段产能。
- 口径风险：最新人员表不等于历史组织归属；调店人员需历史组织数据。
- 隐私要求：不需要证件、电话、银行等字段。

【需求：完整组织架构、门店清单、在职人数】
- MCP先查：MCP无法完整提供
- 需导出：人员信息导出（汇总 + 人员列表）
- 建议字段：运营、大区、片区、门店、分组、职能、姓名、工号、离职/冻结状态
- 时间范围：分析截止日最新快照
- 合并键：组织层级组合；人员用工号
- 计算逻辑：汇总表用于快速人数核对，人员列表用于去重和自定义在职口径。
- 口径风险：汇总人数与人员列表去重人数可能因冻结、离职、无组织人员而不同。
- 隐私要求：最小化保留字段。

【需求：人员活跃、冻结、最近登录分析】
- MCP先查：MCP无法提供人员账号状态
- 需导出：人员信息导出（人员列表）
- 建议字段：工号、姓名、组织层级、离职、冻结、冻结时间、最近登录时间
- 时间范围：最新快照，定期重复导出可观察变化
- 合并键：工号
- 计算逻辑：按最近登录天数分层，并排除离职/冻结账号。
- 口径风险：最近登录不等于实际工作活跃；需结合业务动作指标。
- 隐私要求：无需电话、证件、地址等字段。

================================================================
十一、可直接发送给客户的最小化导出指令
================================================================

【统计值对应具体合同】
- MCP先查：queryRptData + 合同明细 + 业绩分配
- 导出触发条件：统计值与明细合同数不一致，或需要结单/组织字段
- 导出表/Sheet：合同信息导出
- 日期字段：签约日期；如按结单口径则结单日期
- 最小字段：合同类型、合同编号、签约日期、结单日期、结单状态、业绩分配、签约门店、签约小组
- 合并/计算：按合同类型+合同编号去重核对
- 客户指令：请导出【合同信息导出】，筛选【日期字段】为【开始日期】至【结束日期】，保留合同类型、合同编号、签约日期、结单日期、结单状态、业绩分配、签约门店、签约小组。

【按完整组织层级分析合同】
- MCP先查：合同明细/业绩分配
- 导出触发条件：需要运营、大区、片区、门店、分组或职能
- 导出表/Sheet：人员信息导出-人员列表；必要时合同信息导出
- 日期字段：人员表为分析截止日快照；合同表按签约日期
- 最小字段：工号、姓名、运营、大区、片区、门店、分组、职能、离职、离职时间、入职日期
- 合并/计算：优先工号；历史调店需说明当前组织口径
- 客户指令：请导出【人员信息导出】中的【人员列表】，保留工号、姓名、运营、大区、片区、门店、分组、职能、入职日期、离职、离职时间；不要导出身份证、银行卡、地址等无关字段。

【人均成交/人均业绩】
- MCP先查：queryRptData或业绩分配
- 导出触发条件：MCP没有准确人员分母
- 导出表/Sheet：人员信息导出-汇总+人员列表
- 日期字段：统计期对应的人员快照
- 最小字段：汇总：运营、大区、片区、门店、人数；人员列表：工号、姓名、组织、入职、离职、冻结
- 合并/计算：先定义期末/平均/期间在职人数
- 客户指令：请导出【人员信息导出】的【汇总】和【人员列表】两个工作表，并保留组织、人数、工号、姓名、入职日期、离职、离职时间、冻结字段。

【房源方/客源方组织分析】
- MCP先查：合同明细
- 导出触发条件：MCP只返回经纪人姓名，没有双方组织层级
- 导出表/Sheet：合同信息导出
- 日期字段：签约日期
- 最小字段：合同类型、合同编号、双方经纪人、职能、分组、门店、片区、大区、运营、签约日期
- 合并/计算：房源方与客源方分别建维度
- 客户指令：请导出【合同信息导出】，按签约日期筛选目标时间段，保留合同标识、房源方和客源方经纪人及其职能、分组、门店、片区、大区、运营字段。

【已实收业绩/业绩小组】
- MCP先查：业绩分配 + 实收明细
- 导出触发条件：需要总实收业绩、业绩小组或原始业绩门店
- 导出表/Sheet：业绩明细导出-业绩分配
- 日期字段：签约日期；结单分析另保留结单时间
- 最小字段：合同键、经纪人、业绩门店、业绩小组、应收科目、分配类型、比例、分配业绩、总实收佣金、总实收业绩
- 合并/计算：总实收佣金按合同去重，分配行按复合键唯一
- 客户指令：请导出【业绩明细导出】中的【业绩分配】工作表，保留合同键、经纪人、业绩组织、分配类型、比例、分配业绩、总实收佣金、总实收业绩和签约日期。

【实收按签约分组分析】
- MCP先查：实收明细
- 导出触发条件：需要签约分组或可读审核状态
- 导出表/Sheet：实收明细导出
- 日期字段：支付日期
- 最小字段：合同键、科目、状态、签约门店、签约分组、签约人、佣金来源、支付金额、支付日期、票据号码
- 合并/计算：票据号优先用于流水识别
- 客户指令：请导出【实收明细导出】，按支付日期筛选目标时间段，保留合同键、科目、状态、签约门店、签约分组、签约人、佣金来源、支付金额、支付日期和票据号码。

【应收应付科目复核】
- MCP先查：应收应付
- 导出触发条件：需要原始显示值或部门层级核对
- 导出表/Sheet：业绩明细导出-应收应付
- 日期字段：签约日期
- 最小字段：合同键、签约门店、应收金额、应收科目、应付科目、应付金额、签约日期
- 合并/计算：应收金额按合同+应收科目去重
- 客户指令：请导出【业绩明细导出】中的【应收应付】工作表，按签约日期筛选目标时间段，并保留合同键、签约门店、应收及应付科目和金额。

【交易性质/抵押分析】
- MCP先查：合同明细
- 导出触发条件：MCP无交易性质或有无抵押
- 导出表/Sheet：合同信息导出
- 日期字段：签约日期
- 最小字段：合同键、交易性质、有无抵押、签约日期、结单状态、结单日期、成交金额/租金
- 合并/计算：仅补充结构化字段，不从备注猜测
- 客户指令：请导出【合同信息导出】，按签约日期筛选目标时间段，保留合同类型、合同编号、交易性质、有无抵押、签约日期、结单状态、结单日期和成交金额/租金。

================================================================
十二、隐私与最小化原则
================================================================

默认不得导出或展示：完整身份证号、银行卡号、社保账户、公积金号、详细住址、户口地址、紧急联系人和电话、完整门牌号、备注中的敏感内容。
默认脱敏建议：
- 身份证和电话仅保留前3后4。
- 地址只保留到小区；非必要不保留楼栋、单元、房号。
- 人员分析优先保留工号、姓名、组织、职能、岗位、入离职和冻结字段。
- 客户明确有权限且业务必要时，才读取高敏感字段，并在输出中说明用途。

================================================================
十三、可直接写入 SKILL.md 的强制规则
================================================================

- 工具选择：统计指标优先使用 queryRptData；具体合同、财务、业绩和付款明细使用 queryContractFinanceData；房源和小区行情使用对应房源/小区工具。
- 导出触发：只有在MCP字段缺失、组织层级不明确、状态枚举不可解释、统计与明细无法对齐时，才要求客户导出表格。
- 导出指令模板：请导出【表格名称】，筛选【明确日期字段】从【开始日期】到【结束日期】，并保留【所需字段】；不要额外提供身份证、银行卡、详细地址等无关敏感字段。
- 合同匹配：所有合同表统一用“合同类型 + 合同编号”匹配；合同编号先去首尾空格并按文本保存。
- 人员匹配：优先用工号；MCP没有工号时，用姓名与组织字段联合匹配，并输出同名/未匹配清单。
- 口径说明：输出必须标明数据来源、查询/导出时间范围、日期口径、是否拆分查询、是否存在统计与明细差异。
- 隐私保护：默认不展示完整证件号、电话、银行卡、社保、公积金、详细地址、紧急联系人及自由备注中的敏感内容。
- 不可推断：不得把deptName直接解释为门店或小组；不得把总实收业绩等同于分配业绩；不得擅自解释status=0/1。
- 通用公司：所有规则使用通用表名和字段名，不出现任何具体公司、部门、人员或示例数据。
- 文件识别：不要依赖文件名、公司名前缀或默认工作表名；按“文件识别规则”中的表头特征识别模块。
- 字段存在校验：执行分析前先检查所需字段是否真实存在；禁止使用不存在的别名字段替代原始列。
- 一对多合并：合同信息为主表；应收应付、业绩分配、实收、付款均可能一对多。多个子表必须先聚合到目标粒度，再连接主表。
- 应收防重：应收应付表中的应收金额可能随不同应付科目重复，按合同键+应收科目去重后再汇总。
- 业绩防重：业绩分配表中的总实收佣金可能在每个分配行重复，按合同键+应收科目去重；总实收业绩按唯一分配行汇总。
- 人员状态：源表使用离职/冻结字段，不得虚构“在职”列；在职状态应由明确规则推导，并在输出中说明。
- 房源参数：houseTypes、towards、decoration、floorRanges 按字符串数组传参；periodRanges 表示满两年等年限特色，periodUniq 表示满五唯一。
- Excel引用：Excel仅作为人工维护与审计版本；Skill运行时优先读取SKILL.md、详细TXT和TSV字段矩阵。

建议伪代码：
1. classify_request() 判断统计/明细/房源/行情/组织/人员。
2. choose_mcp_tool() 优先选择 MCP。
3. resolve_date_basis() 明确业务日期。
4. validate_required_fields() 检查 MCP 或导出表字段。
5. request_minimal_export() 仅在缺字段时生成导出指令。
6. normalize_keys() 清洗合同号、工号和表头。
7. aggregate_child_tables() 各一对多表先聚合。
8. join_and_reconcile() 合并并核对统计与明细。
9. redact_sensitive_fields() 默认脱敏。
10. report_provenance_and_risks() 输出来源、口径和差异。

================================================================
十四、最终结论
================================================================

常规统计、合同财务明细、房源和小区行情优先使用 MCP。
涉及完整组织层级、人员分母、双方组织归属、交易性质、抵押、房源侧带看、业绩小组或总实收业绩时，必须按需求指导客户导出相应表格。
Skill 的最佳知识文件组合不是单独 Excel，而是：SKILL.md + 详细TXT + TSV字段矩阵 + 可选XLSX维护版。
所有公司通用化时，不写死公司名、部门名、工作表默认名或组织层级值，始终通过表头和字段映射动态识别。
