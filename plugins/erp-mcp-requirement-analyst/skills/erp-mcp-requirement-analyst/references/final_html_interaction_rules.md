# 最终回答必须使用可交互 HTML

## 一、所有正式结果都生成 HTML

只要已经完成查询、计算或分析，就必须生成一个自包含 HTML 结果页。

聊天窗口只保留：

- 一句完成说明；
- HTML 文件入口；
- 必要的严重限制提醒。

不得把完整结果只堆在聊天正文中。即使只有一个核心数字，也要生成轻量 HTML 结果页。

## 二、生成后必须尝试自动打开

标准流程：

1. 写入报告 JSON；
2. 校验 JSON；
3. 渲染 HTML；
4. 静态校验 HTML；
5. 有浏览器自动化能力时，实际打开并点击关键控件；
6. 使用 WorkBuddy 当前可用的“打开产物/浏览器预览”能力自动打开；
7. 若宿主没有打开能力，再尝试系统默认浏览器；
8. 最后在聊天中提供可点击文件入口作为备用。

只有实际打开成功时才能写“已自动打开”。失败时必须如实说明，但仍提供文件入口。

## 三、顶部默认提供筛选入口

每个正式看板必须先判断并尽可能提供：

- 时间范围；
- 公司/组织范围；
- 业务类型；
- 当前任务真正相关的其他维度。

### 时间筛选

- 如果已加载多期数据，可以在页面内直接筛选；
- 如果切换时间必须重新调用 MCP，按钮必须写“按这个时间重新查询”，不能假装在本地已经完成查询；
- 页面要说明当前显示的是哪个时间。

### 组织层级筛选

组织层级必须根据当前公司的真实结构生成：

- 全公司；
- 运营；
- 大区；
- 片区；
- 门店；
- 分组；
- 个人。

实际公司缺少某一层级时就不显示该层级。

组织数据来源可以是：

- 人员信息导出的“汇总/人员列表”；
- MCP 已返回且能可靠识别的部门或人员字段；
- 客户明确提供的组织范围。

没有组织结构数据时：

- 至少显示“全公司”；
- 清楚写“当前没有读取到公司组织架构，暂时不能按片区或门店筛选”；
- 不得生成空下拉框；
- 不得生成看似可用但实际不会改变结果的控件。

### 页面内筛选与重新查询必须区分

- 已加载数据中的筛选：按钮写“应用筛选”；
- 需要重新调用 MCP 且页面已确认具备 WorkBuddy 原生 MCP Apps Widget 或安全桥接能力：按钮写“按当前条件查询”或“实时查询”；
- 需要重新调用 MCP 但页面只是普通本地 HTML：按钮写“复制筛选条件，回到对话继续查询”；
- 需要客户补充允许导出的表格：按钮写“查看需要补充的表格”；
- 当前无法实现：显示说明，不生成假按钮。

### 实时查询必须有安全桥接

普通 `file:///dashboard.html` 不能直接连接当前会话的 ERP MCP。它没有 WorkBuddy 会话工具、没有授权通道，也不能安全保存 ERP Token。

如果客户要求页面里直接查询 ERP，必须优先生成或调用 WorkBuddy 原生 MCP Apps Widget。Widget 可以通过 Host 提供的安全桥接调用 MCP 工具，查询结果再更新页面。

如果没有检测到 Widget/桥接能力：

- 不得把按钮写成“按此条件重新查询”；
- 不得在 HTML 里写 ERP URL、Authorization 或 Token；
- 不得暗示浏览器会直接读取 ERP；
- 必须显示普通中文说明，并提供回到对话继续查询的指令。

相关详细规则见：`references/mcp_apps_widget_rules.md`。

## 四、失败时绝不能显示假 0

脚本报错、JSON 缺字段或页面数据未加载时：

- 显示“加载失败”“等待查询”或“暂无可验证数据”；
- 不得把缺失值默认成 0；
- 只有真实查询结果确实为 0 时，才能显示数字 0，并必须带来源说明。

## 五、筛选入口必须真的可用

生成后至少验证：

- 时间选择；
- 组织层级选择；
- 业务类型选择；
- 应用筛选或重新查询按钮；
- 数字详情；
- 返回总览；
- 搜索；
- 导出按钮。

没有数据选项的下拉框必须隐藏或显示说明，不能保留空白控件。

## 六、实时看板优先级

当同一份结果既可以做普通 HTML，也可以做 MCP Apps Widget 时：

1. 优先使用 MCP Apps Widget，因为它能在页面内安全调用 ERP；
2. 只要页面有时间、层级、业务类型切换、重新查询、数字明细钻取等常见交互，就必须先判断 Widget 是否可用；
3. 如果 Widget 工具不存在或宿主不支持，退回普通 HTML；
4. 普通 HTML 仍可做本地筛选、搜索、明细查看和导出；
5. 普通 HTML 不做实时后台查询，也不伪装成实时后台查询。
